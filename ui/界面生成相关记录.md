## 三处必要的核心库修复

1. **非分块任务直接崩溃**：[IDownloadExecutor.kt](file:///E:/github/AppUpdateChecker/core/src/main/java/com/github/knightwood/downloader/core/executor/IDownloadExecutor.kt) 中 `create(conf)` 在未开分块时把 `chunkCount` 传 0，`check(chunkCount > 0)` 会抛异常。改为退化为 1（单连接）。
2. **排队中的任务无法停止**：[DownloadService.kt](file:///E:/github/AppUpdateChecker/core-android/src/main/java/com/github/knightwood/downloader/core/android/service/DownloadService.kt) 的 `cancelTask` 只调用 `task.cancel()`，任务仍在 `pending` 队列里照常开始下载；改为 `taskMgr.cancel(id)`（会先从等待队列移除）。
3. 未改动但需注意：`AndroidUriRandomAccessFileStorage.writeAt` 忽略了 `pos` 参数，用于 uri 随机写是错的；由于 `MultiChunkDownloadExecutor` 会检查 `fileStorage is RandomAccessFileStorage` 并自动退化为单连接，目前不会写坏文件，因此界面在 SAF/MediaStore 下也强制关闭分块开关。

## 行为说明

- **实时进度**：`stateFlow` 的 `DOWNLOADING` 约 200ms/1s 发射一次，落库按 500ms 节流；状态变化（开始/暂停/停止/完成/失败）立即写入，并记录分块进度（暂停、停止、失败时）。
- **旧记录加载**：列表数据源就是 `download_task_table`，进程重启后仍可见；数据库里记录为“下载中”但服务中已不存在的任务会被标记为“已暂停”。
- **保存位置**：缓存目录（`externalCacheDir/Download`，无需权限）、系统下载目录（Android 10+ 走 MediaStore、以下走文件路径 + 存储权限）、SAF 目录（`ACTION_OPEN_DOCUMENT_TREE` + 持久化授权 + `DocumentsContract.createDocument`）。
- **多线程判断**：`HttpConnectionUtils.probe` 返回的 `acceptRanges` 决定开关是否可用，并自动填充文件名；保存位置不支持随机写或文件小于 1MB 时给出对应提示并禁用开关。
- **断点续传暂未启用**：暂停/继续在同一服务进程内有效；`DownloadServiceLinker` 未暴露“带进度恢复地提交任务”，因此对已停止/失败的记录点“重新下载”会以原任务 id、原保存位置从 0 重新写入（避免在 `submitTask` 与 `restoreProgress` 之间产生竞态）。若需要真正的续传，需要在 core-android 增加支持传入 `DownloadTaskSaveState` 的提交接口。

# UI界面中那些正在下载的任务，显示下载进度可以从DownloadTask中的currentDownloadingProgress或者progress或者stateFlow读取，不要在obseveTask中计算，也不要将下载进度写入数据库

明白，改成“进度只在内存中流转、由 `DownloadTask` 本身提供”的方案。先让 `DownloadTask` 暴露最近一次下载中的进度快照：`DownloadTask.currentDownloadingProgress` 现在已是 `StateFlow` 形式，正好可以直接作为进度源。先查看仓库文件现状：现在改造 Repository：进度只在内存中发布，数据库只记状态。现在把 ViewModel 的列表数据源改为“数据库记录 + 内存实时状态”：数据库实体被调整过，检查一下实体与 DAO 的列名：界面已能通过 `task.progress` 显示实时进度。再微调一下文案，避免“无进度记录”的历史任务显示成 `0 B / 12 MB (0%)`：已按要求改造完成，进度现在完全走内存，数据库只存状态。

## 核心变化

**1. 进度来源：直接读 `DownloadTask` 的两个流**

`DownloadTask` 目前已经暴露了两个可观察源，仓库只做"搬运"，不做任何计算：
- `stateFlow: StateFlow<DownloadStatus>` —— 状态（含 `DOWNLOADING.length/progress/snapSpeed/chunks`）
- `currentDownloadingProgress: StateFlow<DOWNLOADING?>` —— 最后一次下载中的快照（暂停/停止后仍保留）

[DownloadTaskRepository.kt](file:///E:/github/AppUpdateChecker/ui/src/main/java/com/github/knightwood/downloader/ui/repository/DownloadTaskRepository.kt) 中 `observeTask()` 简化为：

```kotlin
combine(task.stateFlow, task.currentDownloadingProgress) { status, progress ->
    TaskRuntimeState(status, progress)
}
    .takeWhile { runtime -> !runtime.status.isTerminalState }
    .collect { runtime ->
        publishRuntime(task.id, runtime)          // 内存：界面实时读取
        if (runtime.status !is DownloadStatus.DOWNLOADING) {
            writeStatus(task.id, runtime.status)   // 只写状态，不写进度
        }
    }
```

新增 `runtimeStates: StateFlow<Map<Int, TaskRuntimeState>>`（key 为 taskId）作为界面读取实时进度的唯一入口；`detach()`、`delete()` 会清理对应条目。

**2. 数据库不再记录进度**

- 删除 `writeProgress()` 与 `PROGRESS_WRITE_INTERVAL`。
- `writeState()` → `writeStatus()`：只调用 `updateStatus()` / `markStarted()` / `markEnded()`，不再 `updateProgress`、不再写 `DownloadChunkEntity`。
- DAO 中删除 `updateProgress()`（这也顺带修好了当前 `:ui:kspDebugKotlin` 的报错：该语句引用了已被注释掉的 `snap_speed`/`average_speed` 列）。

**3. 界面合并展示：数据库记录 + 内存状态**

[DownloadMgrScreenViewModel.kt](file:///E:/github/AppUpdateChecker/ui/src/main/java/com/github/knightwood/downloader/ui/screen/DownloadMgrScreenViewModel.kt)：

```kotlin
val tasks = combine(dao.observeAll(), repository.runtimeStates) { records, runtimeStates ->
    records.map { record -> record.toUiItem(runtimeStates[record.taskId]) }
}
```

`toUiItem(runtime)` 的取值规则：
- 进度 / 速度 / 状态：优先用 `runtime.progress`（`length`、`progress`、`snapSpeed`）与 `runtime.status`
- 没有运行时状态（进程重启后的历史记录）：状态用数据库值，总长度用 `size`，下载量为 0
- 已完成但无运行时进度：按文件长度视为 100%

[DownloadMgrScreen.kt](file:///E:/github/AppUpdateChecker/ui/src/main/java/com/github/knightwood/downloader/ui/screen/DownloadMgrScreen.kt) 的进度条保持 `LinearProgressIndicator(progress = { task.progress })`；摘要文案调整为：无进度记录时只显示文件大小，不再出现 `0 B / 12 MB (0%)`。

## 行为说明

- 下载中：列表约每 200ms（分块）/ 1s（单连接）刷新一次进度、百分比、瞬时速度，全部来自 `stateFlow`，零数据库写入。
- 暂停 / 停止：`currentDownloadingProgress` 保留最后一帧，进度条停在原位；数据库只写入 `PAUSED` / `CANCELED` 状态。
- 进程重启：历史记录从数据库加载（状态、文件名、大小、保存位置），进度不再保留——这是不落库的必然结果，重新下载会从 0 开始。

## 验证

- `:ui:assembleDebug` → `EXIT=0`
- `GetProblems`：改动文件无错误

**[DownloadMgrScreenViewModel.kt](file:///E:/github/AppUpdateChecker/ui/src/main/java/com/github/knightwood/downloader/ui/screen/DownloadMgrScreenViewModel.kt)**

`NewTaskUiState` 新增上限推导与收敛逻辑：

```kotlin
val maxChunkCount: Int
    get() = maxChunkCountOf(meta?.length ?: 0L)

companion object {
    const val MIN_CHUNK_COUNT = 2
    const val MAX_CHUNK_COUNT = 128          // 原来 VM 里的 MAX_CHUNK_COUNT = 8 已删除

    fun maxChunkCountOf(length: Long): Int {
        if (length <= 0L) return MIN_CHUNK_COUNT
        return (length / HttpConstant.MIN_CHUNK_SIZE)
            .toInt()
            .coerceIn(MIN_CHUNK_COUNT, MAX_CHUNK_COUNT)
    }
}
```

配套调整：
- `onChunkCountChanged`：`count.coerceIn(MIN_CHUNK_COUNT, state.maxChunkCount)`
- `probe()` 成功后调用 `.normalized()`：探测到大文件后自动保留原选择，探测到小文件时把超出上限的值收敛下来（未探测到尺寸时不处理，避免把默认值 4 提前压成 2）
- `submitNewTask()`：提交时再次按实际 `meta.length` 收敛 `maxChunkCount`，确保每块不小于 `MIN_CHUNK_SIZE`

## 行为说明

| 文件大小 | 滑块上限 | 说明 |
|---|---|---|
| ≤ 1 MB | 不启用分块 | `chunkAvailable` 为 false，开关置灰 |
| 2 MB | 2 | 只显示提示文字，无滑块 |
| 100 MB | 100 | 2 ~ 100 可调 |
| ≥ 128 MB | 128 | 封顶 128 |

上限公式与 core 中 `MultiChuckDownloadExecutor` 的实际切块逻辑一致（`actualChunks = min(chunkCount, totalLength / minChunkSize)`），所以界面上选定的块数就是最终生效的块数，不会被二次截断。

一点提示：`MultiChuckDownloadExecutor` 会为每个分块并发 `async` 发起连接，选到 100+ 块时等于同时开 100+ 个 HTTP 连接（`minChunkSize` 为 1MB，所以只有 128MB 以上的文件才会触及高位）。如果实际网络环境扛不住，可以后续在 core 里给分块下载加一个并发上限（如 `Semaphore(8)`），界面上的分块数保持不变。
